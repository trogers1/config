= Config

Herein lies my configuration files 📜

== Layout

* `home/` contains files that should be symlinked into `~/` (including selected nested app configs like `home/.cursor/cli-config.json` → `~/.cursor/cli-config.json`, `home/.pi/agent/settings.json` → `~/.pi/agent/settings.json`, `home/.pi/agent/packages/pi-guard` → `~/.pi/agent/packages/pi-guard`, and `home/.pi/agent/packages/pi-guard-subagents` → `~/.pi/agent/packages/pi-guard-subagents`)
* `home/.agents/` holds the skills, prompt snippets, and subagents shared by Pi, Claude, and OpenCode; `home/.claude/` holds Claude config, mostly generated from it (see link:./home/.agents/README.adoc[`home/.agents`])
* `xdg/` contains application configs that should be symlinked into `~/.config/`
* `tmux_and_worktrees/` contains my tmux + git worktree development workflow (tooling built specifically for parallel agentic workflows)

== Setup

The shared macOS/Linux setup and personal macOS linker have deliberately different ownership boundaries.
Run the safe, additive shared setup with:

[source,bash]
----
./setup.sh
----

Run the separate personal-dotfile linker only on machines where this repository
should own the complete personal configurations:

[source,bash]
----
./setup-personal.sh
----

The personal installer has a stable, explicit manifest for home, XDG, Cursor,
and Pi guard profile/prompt configuration. It does not invoke shared setup and
does not install Pi packages, command wrappers, or worktree resources. To install both sets, run
both commands explicitly. Both support `--status`, `--verify`, `--dry-run`, and
`--uninstall`.

=== Breaking setup migration

The former setup scripts and `--mode` interface have been removed. Existing
installations must run the explicit, one-time migration before the new shared
setup:

[source,bash]
----
./scripts/setup/migrate-legacy.sh
----

The migration splits the old whole `pi-guard` link while preserving
`profiles.jsonc`, backs up regular shell/tmux files before removing known old
marker blocks, and removes old `d*` wrappers only when their exact content
matches an installer-generated wrapper. Normal `./setup.sh` detects known
legacy state and exits before changing files.

== Shared dev + Pi setup (macOS/Linux)

The safe shared Pi and non-writing tmux/worktree workflow is installed with:

[source,bash]
----
./setup.sh
----

This macOS/Linux installer has an explicit, limited surface: it installs the
shared Pi configuration (packages, extensions, settings, and usage), the
shared `~/.agents` skills and snippets, the Claude skills, subagents, and
hooks (registered in a user-owned `~/.claude/settings.json` without changing
its other keys), the `dev` CLI, and the tmux status helper. The personal
installer additionally links the complete Claude settings and the global
`CLAUDE.md`/Pi `AGENTS.md` instructions. It does not install or link Cursor, Git, Ghostty,
Neovim, OpenCode, or shell dotfiles. `wopen`, `wnew`, and `wclose` are excluded.

Before changing configuration it requires `tmux` (3.5+), `git`, `python3`, and
`node`/`npm` (Node 22.19+). Existing Pi must be 1.3+. The managed tmux block uses `extended-keys on`
and `extended-keys-format csi-u`, which requires tmux 3.5 or newer.
Restart the tmux server after upgrading/configuring it (save work first);
verify Shift+Enter inserts a newline and Enter submits inside Pi. Missing tools cause a nonzero exit before
modification. Neovim and lazygit are optional, workflow-specific tools; setup
does not require them, but warns when they are absent and shows the optional
`brew install neovim` or `brew install lazygit` command.
When `pi` is missing, normal `./setup.sh` automatically downloads the official
https://pi.dev/install.sh installer to a temporary directory and runs it with
`sh`, after Node/npm and setup preflight pass. `curl` is required for this
case; no separate install flag is needed. `--dry-run` only prints the plan.
The downloaded script is cleaned up on success or failure.

New installations use Pi's managed release layout under `~/.pi/agent/install`
and its launcher at `~/.pi/agent/bin/pi`, which setup adds to its own PATH
immediately. Unlike `npm install -g` under nvm, the Pi installation is not tied
to one nvm Node version's global package directory. Node/npm must still be
available for setup and Pi runtime/update operations. Ensure
`~/.pi/agent/bin` remains on your shell PATH. The installed shared `.zshrc`
block (and the personal zsh configuration) prefers
`${PI_CODING_AGENT_DIR:-$HOME/.pi/agent}/bin` when its Pi launcher exists,
including after directory changes and at prompts following nvm switches.
Fresh interactive zsh shells therefore find managed Pi without personal
dotfiles or inheriting setup's PATH. Node executable selection is unchanged.
Update managed Pi with `pi update`.

After migrating an existing npm installation, restart your shell and verify
`command -v pi` selects the managed launcher and `pi --version` succeeds.
Old nvm-global npm copies may remain: remove them manually, one Node version
at a time, only after confirming they are no longer needed. Keep any copy
used by a currently running Pi process until that process has exited; setup
does not remove it automatically.

Run `bash tests/setup.test.sh` for the setup gate (requires zsh for the
personal PATH checks). It includes the network-free managed installer tests
and `tests/managed-pi-path.test.sh`, which verifies managed Pi precedence
across simulated nvm switches, deduplication, custom agent directories, and
unchanged command resolution when managed Pi is absent.

Existing working installations are preserved, regardless of installation
method; setup never silently migrates, reinstalls, or uninstalls them. Outdated,
broken, off-PATH, or partial installations fail with explicit repair/update
instructions. Download/installer failures stop before shared configuration is
installed; a partial upstream installation may need explicit repair before
retrying. `--uninstall` removes shared configuration, not the Pi installation.
Native Windows remains separate: use `setup.ps1` with an existing Pi 1.3+;
the managed shell bootstrap is macOS/Linux only.

The shared setup also installs the dev-session Pi extension and Claude
`SessionStart` metadata hook. `dev new`/`open`/`tree` persist session intent;
`dev resume-all` restores missing sessions detached after a reboot, using only
the configured agent pane's exact recorded Pi file or Claude session ID.
Intentional dev closures unregister sessions; crashes do not. Existing sessions
from before tracking cannot be guessed. See
link:tmux_and_worktrees/README.adoc#_persistent_sessions_and_reboot_recovery[recovery and bootstrap caveats].

The local Pi packages have dependencies that are not committed. A fresh clone
will fail the dependency preflight without making changes. After reviewing the
packages, bootstrap those dependencies explicitly:

[source,bash]
----
./setup.sh --bootstrap-pi-deps
----

That command runs `npm ci` in each bundled Pi package (with
`--ignore-scripts --legacy-peer-deps` for the locally owned `pi-claude` SDK provider) and downloads Playwright
Chromium for `pi-webfetch`; it is never implicit. Use `--dry-run` to print the
planned changes, `--status` to inspect current managed links/wrappers, and
`--uninstall` to remove unchanged installer-owned artifacts.

When a selected link or wrapper target already exists, normal setup prompts
before moving it to an adjacent `<target>.bak` backup. For an existing regular
`~/.zshrc` or `~/.tmux.conf`, it instead prompts before preserving the file in
place, copying it to `<target>.bak`, and appending only its marked managed
block. `--non-interactive` fails on every such conflict rather than silently
skipping or replacing a file. Existing `.bak` files are never overwritten.
Uninstall removes only a replacement that is still installer-owned and
unchanged. Adjacent backups are preserved for explicit manual restoration;
the installer never promotes an untracked `.bak` file into active configuration. The installer
never overwrites `~/bin/pi` and never follows a symlinked `~/.zshrc` or
`~/.tmux.conf` to edit its target.

The installer adds only uniquely marked blocks to a regular `~/.zshrc` (PATH,
`dev home`) and regular `~/.tmux.conf` (CSI-u extended-key settings and the workflow include). If either file is a symlink owned by `setup-personal.sh`, shared setup recognizes the checked-in configuration as providing the integration and does not edit through the link. It does not reload
an existing tmux server; reload deliberately after reviewing the changes:
`tmux source-file ~/.tmux.conf`.

Pi resources installed here are global and therefore trusted by Pi for all
projects. Option/Alt shortcuts depend on the terminal reporting Option as
Meta, which is not macOS's default. The shared extensions therefore provide
`Ctrl+Shift` fallbacks for every shared slash command and shortcut; see each
package's README for the command map. Run `./setup.sh --verify` after opening a new terminal to check every declared shared artifact. The included skills, browser tool, and usage tooling reflect
the current repository configuration; review changes under `home/.pi/` as
privileged executable configuration. `dev tree` also retains its existing fallback
initializer, which may link `.env`/Terraform files and run `npm ci` when it
creates a worktree.

== Shared dev + Pi setup (Windows)

For native Windows, run the PowerShell shared installer from a PowerShell prompt:

[source,powershell]
----
.\setup.ps1
----

It installs the same explicitly listed shared Pi resources (settings, models,
skills, usage, packages, and extensions), with the same
conflict backup, `-DryRun`, `-NonInteractive`, `-Status`, `-Verify`,
`-Uninstall`, and explicit `-BootstrapPiDeps` behavior. It requires Git, Pi 1.3+, Node/npm 22.19+,
and permission to create symbolic links. Enable Windows Developer Mode or run
PowerShell elevated if its symbolic-link preflight fails. Both team installers
leave `~/.pi/agent/pi-guard/profiles.jsonc` user-owned; Pi falls back to its
portable built-in profiles when that file is absent.

The Windows installer deliberately does *not* install `dev`, tmux configuration,
or zsh integration: those are Bash/tmux-specific
and remain supported only by the macOS installer. If your execution policy
blocks local scripts, run it explicitly with:
`powershell -ExecutionPolicy Bypass -File .\setup.ps1`.

== link:./tmux_and_worktrees[Tmux and Worktrees]

This config includes my development tmux+worktree setup for parallel agentic development. Install the shared workflow with link:./setup.sh[`./setup.sh`]. Personal dotfiles are installed separately by `./setup-personal.sh`; see link:./tmux_and_worktrees/README.adoc[the README] for instructions and dependencies.

Use `dev --list` to discover live/saved dev sessions and the current repository's
Git worktrees. `dev switch` starts with OPEN sessions in `fzf` (tmux popup inside
tmux, terminal otherwise). Ctrl+A toggles ALL sessions/worktrees while retaining
the search query, even if no sessions are open. Select an open session, exactly
restore just one saved session, or open an available checkout. Scope toggles and
Esc/Ctrl-C cancellation do not change session/registry state.
Open the picker with `prefix + w`, using either Meta+Space or Ctrl+B as the
prefix. The existing `prefix + s` tmux chooser is unchanged; see
link:./tmux_and_worktrees/README.adoc#_finding_and_switching_sessions[discovery and picker behavior].

= Dev Config: tmux + git worktrees

This directory contains a portable tmux/worktree workflow you can copy into its own repo.

== What it sets up

The `dev` CLI is the primary interface:

* `dev new [--agent <name>] [path]` -> normal dev tmux session in the current repo/path
* `dev open [path]` -> alias for `dev new`
* `dev tree [--no-attach] [--agent <name>] [--stage-agent] <branch> [base]` -> create/switch to a git worktree + tmux session (defaults base to current branch)
* `dev tree init [branch]` -> rerun the worktree startup script (defaults to the current branch's worktree)
* `dev close [branch|path]` -> kill the tmux session only, leaving the checkout/worktree intact
* `dev kill [branch|path] [--force] [--yes]` -> kill the worktree tmux session and delete that worktree + local branch
* `dev merge [branch|path] [target] [--keep]` -> interactively choose merge target and clean up
* `dev --list` -> list open/saved dev sessions and the current repository's Git worktrees
* `dev switch` -> fuzzy-pick OPEN sessions; Ctrl+A toggles ALL sessions/worktrees (requires `fzf`)
* `dev resume-all` -> recreate missing registered sessions detached, with their exact recorded agent conversations
* `dev home` -> jump the current shell back to the root path for the active tmux dev session
* `dev help` (or `dev --help`) -> display usage and command descriptions

`dev home` is only available inside a tmux dev session created by `dev new`,
`dev open`, or `dev tree`; it needs the installed zsh shell integration because
changing directories must happen in the current shell.

* `wopen` -> `dev new`, but launch `nvim` with `NVIM_COLORSCHEME=shine`
* `wnew` -> open a new Ghostty window with writing overrides, then run `wopen`

Writing-mode `nvim` overrides are passed explicitly by `wopen`/`wnew`, so plain
`dev new` does not depend on inherited shell environment for editor mode.

Each dev session opens tmux windows from `devConfig.jsonc`.
By default, this subsystem uses `tmux_and_worktrees/devConfig.jsonc`:

[source,jsonc]
----
{
  "defaultAgent": "pi",
  "agents": {
    "pi": "pi",
    "claude": "claude --continue || claude"
  },
  "windows": [
    { "name": "nvim", "command": "nvim" },
    { "name": "agent", "agent": true },
    { "name": "lazygit", "command": "lazygit" },
    { "name": "term", "command": "" }
  ]
}
----

Add a project-specific `devConfig.jsonc` at the repo/worktree root to override
the whole file for that project. `windows` is an array of objects with:

* `name` -> tmux window/tab name
* `command` -> command to run in that window; use an empty string for an idle shell
* `agent: true` -> instead of `command`, run the selected agent (at most one agent window per config)

The agent window runs the command for the agent you pick per run with
`dev new --agent <name>` or `dev tree --agent <name>`, and otherwise the
config's `defaultAgent`. That is also the per-project choice: a project's
`devConfig.jsonc` sets its own `defaultAgent` and `agents`.
`dev tree --stage-agent` types the agent's command into its window without
pressing Enter, so the agent starts only when you do; the other windows run as
usual. When the config cannot provide an agent (an unknown `--agent`, an agent
window with no `defaultAgent` and no `--agent`, or `--agent <name>` with a
config that has no agent window), dev prints a warning on stderr and opens the
session anyway, with the agent window, if any, as an empty shell. Any other
invalid config fails before anything is created. `dev tree` reads a new
worktree's config before `git worktree add`: the `devConfig.jsonc` committed at
the commit the worktree starts from, or the bundled default, so a config the
startup script writes later is not used. `--agent` and `--stage-agent` apply
only when a new session is created;
reopening an existing session says so and keeps its windows.

`claude --continue` resumes the most recent conversation recorded for the
worktree directory, so closing a session (`dev close`) and reopening it with
`dev tree` picks the conversation back up. In a directory with no conversation
yet, `claude --continue` prints `No conversation found to continue` and exits
non-zero, so the configured command then starts a new one.

`dev close`, `dev kill`, and `dev merge` find worktrees with
`git worktree list --porcelain`, not dev's directory convention, so they also
work on worktrees other tools made, such as Claude Code's
`<repo>/.claude/worktrees/<name>`. Each takes a branch or a path inside the
worktree; a path names its own repository, so it works from any directory, and
it is the only way to name a detached worktree. A target is a path only when it
is an existing directory written as `.`, `..`, or with a `/` (`./docs`, not
`docs`), so a bare name is always a branch even if the current directory has a
folder of that name. A path that is also a different branch's worktree is
rejected as ambiguous. With no argument,
`dev kill` and `dev merge` act on the worktree they run in.

Session reuse and cleanup are path-based first: `dev new`, `dev tree`,
`dev close`, `dev kill`, and `dev merge` all resolve the owning tmux session by
`DTREE_WORKTREE_PATH` before falling back to the preferred human-readable
session name.

== Fresh sessions with initial assignments

`dev new`, `dev open`, and `dev tree` accept mutually exclusive
`--prompt <text>` and `--prompt-file <path>` options. These always start a
fresh Pi or Claude conversation; they never continue an unrelated conversation.
`--no-attach` and `--stage-agent` are also available on all three commands.
Launch is immediate unless `--stage-agent` is supplied.

[source,sh]
----
# Use an exact, already-verified source commit rather than a moving branch.
source_commit="$(git rev-parse HEAD)"
dev tree --no-attach --agent pi --prompt-file ./handoff.md -- RI-455 "$source_commit"

# Prepare an inert launch; press Enter in the configured agent pane to start.
dev open --no-attach --agent claude --stage-agent --prompt 'Inspect the checkout and propose a plan.' .
----

Prompt-bearing launches support configured commands `pi`, `claude`, and the
bundled `claude --continue || claude`. The bundled Claude expression is replaced
with one fresh invocation, without a continue attempt or fallback retry. Other
configured wrappers, flags, and shell expressions fail explicitly before a new
checkout is created. Launches without prompt options retain their existing
configured-command behavior, including the Claude continue/fallback command.
A prompt requires one enabled, supported agent window and an installed executable;
unknown agents do not silently produce an empty shell for this launch mode.
An already-open session rejects prompt options rather than ignoring them.

The assignment is snapshotted into a unique private directory under
`${XDG_STATE_HOME:-$HOME/.local/state}/dev/launches`. Directories are `0700` and
files are `0600`; the published manifest and prompt are validated before launch.
Deleting or editing the original `--prompt-file` after staging does not change
the assignment. Missing, empty, invalid UTF-8, or altered durable input fails
explicitly. Staged shells contain only a safely quoted single-line helper
command, never the raw prompt. Newlines, Unicode, and shell metacharacters in
an assignment cannot execute shell commands during staging.

Pi receives its documented `@file` initial input (including Pi's file-context
framing); Claude receives the snapshot as a positional prompt. Neither adapter
requires the model to read the state directory through a filesystem tool.
Native Claude permissions remain unchanged. Without `--agent-profile`, Pi keeps
its existing automatic profile selection; the launching session's active profile
is not inherited as a new default. An explicit `--agent-profile <name>` is Pi-only
and selects pi-guard's initial profile, not a permanent pin. Claude rejects it
rather than translating it into a native permission mode. The flag works with
or without a prompt. It is validated before checkout/session creation and again
when a staged command is executed. Unknown profiles, unavailable integration,
and conflicting authoritative subagent selection fail explicitly.

The first implementation supports the enabled, unfiltered user-local pi-guard
package installed by this repository's setup. Project guard overrides, remote
npm/git installations, extension filters/autoload overrides, ambiguous aliases,
and non-builtin top-level extension paths are rejected rather than guessed or
silently enabled. All package declarations must use available explicit local
paths; bare relative sources and remote package sources are rejected, including
unrelated packages whose identities cannot be proved safely. Guard extension
roots with ignore files, package entrypoints, or index entrypoints are also
rejected because they can hide `guard.ts`. New-worktree preflight rejects committed project
extensions and relative `PI_GUARD_PROFILE_CONFIG`; an absolute override can be
validated before that checkout exists. Ordinary unrelated user auto-discovered
extensions remain supported. No `-e` injection enables a disabled guard.
See pi-guard's startup-option documentation for exact precedence and later
profile switching.

A never-attempted staged launch can be recovered with its original assignment.
Before executing the agent, the helper durably records an attempt. If no exact
conversation was recorded after an attempt, recovery fails instead of replaying
the kickoff, even if startup failed. Once a conversation is recorded, recovery
resumes only that conversation and does not need or replay the kickoff artifacts.
Exact recovery does not reapply a kickoff's startup-profile override; normal
session-profile persistence and directory selection govern the resumed process.
Editor overrides apply only to ordinary editor windows, never an agent-role
window, even if that agent window is named `nvim` (an intentional role-based
behavior change).
Closing sessions does not delete launch artifacts; retain them while a staged
command depends on them. No automatic artifact garbage collection is provided.

Supplying an assignment does not prove the agent completed it or enforce a
model-level planning gate. `dev` remains generic: ticket retrieval and workflow
instructions belong to the shared skills, not this CLI.

== Starting a ticket: plan-first or explicit direct implementation

Both agents discover the same shared `start-ticket` and `implement-plan` skills.
Pi uses `/skill:start-ticket` and `/skill:implement-plan`; Claude uses
`/start-ticket` and `/implement-plan`. For example, in Pi:

[source,text]
----
/skill:start-ticket RI-455 based on my current branch, using Pi
----

The skill reads the ticket through the existing `jira-ticket` CLI, records the
canonical ticket identity and exact committed source HEAD, and carries only
relevant context into a private handoff. It checks dirty source changes and
existing ticket branches/worktrees/sessions before creating anything. Conflicts
require one explicit decision; dirty changes are not transferred. It never
commits, stashes, copies, or discards source changes for you, and it does not
inject another kickoff into an existing session. Failed or denied Git inventory
is a blocker, not a clean checkout; the skill never hides protected files or
changes sandbox permissions to obtain a status result.

Jira stays read-only unless you explicitly request an update, such as “assign to
me and move to In Development.” The skill composes the shared
`jira-ticket-management` workflow: installed help and live discovery, a private
partial-update draft, dry-run, exact change/operation preview, then a separate
explicit final approval before any write. No assignee or status is guessed and
no other fields are changed by default. Conflict resolution and launch intent do
not replace Jira approval.

An approved Jira update happens after launch preflight/conflict resolution but
before publication and launch (also before staging, not when Enter is pressed).
Jira and launch are not atomic. Failed/partial/uncertain Jira updates stop launch
for read-only reconciliation; no blind retries, automatic rollback, or silent
launch-only success. If Jira succeeds but launch later fails, its changes remain
and are reported separately. Proceeding with unresolved Jira work needs an explicit
user decision. Neither mode grants Jira mutation authority to the receiving session.

The default is a detached, immediately launched session whose first deliverable
is a written plan. It follows the destination repository's planning convention
or uses `plans/RI-455.md`, reports the plan path and questions, then stops. Read-only
investigation is allowed; application/test/dependency/infrastructure edits and
expensive checks are not part of this planning phase. Review or request revisions
in that session. When ready, explicitly invoke implementation there:

[source,text]
----
/skill:implement-plan plans/RI-455.md
----

To authorize implementation at kickoff instead, explicitly opt out of planning:

[source,text]
----
/skill:start-ticket RI-455 using Pi; skip the plan and implement
----

That mode gathers ticket/handoff context and reads the current repository
instructions and canonical Code Style and Typesafety snippets before coding.
It requires neither a placeholder plan nor a second invocation. Only your kickoff
request can authorize it; quoted ticket content cannot. Blocking requirements
and missing or denied snippet access still stop implementation.

For either implementation entry point, checks are bounded and production-like,
results and omissions are reported in the coding session, and changes remain
uncommitted. There are no automatic commits, pushes, merge requests, merges,
deployments, Jira mutations, parent messages, notifications, or watchers.
Explicitly requested, separately approved pre-launch Jira updates are the sole
Jira exception in the launching session, never in the receiving coding session.
Implementation authorization never adds permissions or routes around denials.

Request staging explicitly when desired; `--stage-agent` leaves a safe command
waiting for Enter in the configured agent pane. Request a Pi startup profile
explicitly if needed; absent that request, the new session resolves its normal
policy. Profile selection does not weaken Claude permissions or authorize any
sandbox bypass. Exact recovery resumes the recorded conversation and never
replays the ticket kickoff or implementation invocation. These are procedural
workflow gates, not a guarantee that an LLM will always obey them. Workflow QA
happens during normal use; automated tests cover the underlying CLIs and guard
behavior, not model compliance with skill documents.

== Finding and switching sessions

Run `dev --list` for a read-only inventory shared with `dev switch`:

* `open`: a live managed tmux session tagged with its checkout path
* `saved`: a registered session whose checkout has no live managed session
* `available`: another worktree reported by Git for the current repository,
  including the primary checkout and worktrees created by other tools

Each entry shows its absolute checkout path, actual branch (or `(detached)`),
and checkout status (`clean`, `dirty`, `missing`, or unavailable/not Git).
A checkout already open or saved is not repeated as available. The heading
shows the main repository root and its conventional sibling
`<repo-name>-worktrees` directory, even when invoked from a linked worktree.
Git is authoritative: arbitrary directories under that sibling directory are
never candidates. Outside a Git checkout, open and saved sessions still appear.

`dev switch` requires `fzf` (`brew install fzf` on macOS). Use a recent fzf
with `--tmux` support: inside tmux it opens a popup; elsewhere it uses the
terminal. The picker starts with *OPEN sessions only*. Press *Ctrl+A* to toggle
between OPEN and ALL (open/saved sessions and available worktrees). The prompt
and header identify the current scope and the next toggle action. Your search
query is retained across toggles. Even with no open sessions, the picker stays
available so Ctrl+A can reveal saved sessions/worktrees. `dev --list` always
shows the full detailed inventory, including clean/dirty Git status, independent
of picker scope. Initial OPEN reads live managed tmux metadata and the small
saved registry for opening order: no Git checkout/status scans or
current-repository discovery.
Ctrl+A discovers ALL on demand, displaying *Loading available sessions/worktrees…*
and fzf's native spinner while it runs. Returning to OPEN or cancelling stops
in-flight discovery. Failures replace Loading with an actionable error; details
are printed on exit. Each switch to ALL discovers fresh data, without a cache.

With an empty query, known sessions follow their original opening order in the
saved registry, not alphabetical or most-recently-used order. ALL keeps open and
saved sessions in that same order, followed by never-opened available worktrees;
OPEN shows only the live subset. Recovery/re-registering preserves positions,
while an intentional close forgets the entry and reopening appends it. A confirmed
fresh workspace starts with only its successful target, then later openings append.
Live tagged sessions predating tracking remain visible after known records, in
tmux creation order (session id breaks same-second ties). The current session has
no special position. Nonempty queries still use standard fzf match ranking.

Columns are space-aligned across both scopes, accounting for wide/combining
characters. SESSION and BRANCH are capped at 32 display cells, including a
trailing `…` for longer names; paths remain unshortened. Only picker display
names are shortened: selection still uses the exact session and checkout path,
and `dev --list` shows full names. Search by the displayed session, branch, or
path, then press Enter. Picker scopes do not scan or display
clean/dirty status; OPEN uses tmux's stored branch, while saved/available entries
use cheap Git branch metadata:


* Open session: attach from a terminal, or switch clients inside tmux.
* Saved session: restore *only that session*, using its exact recorded agent
  conversation, then connect after recovery has completed. A missing checkout,
  transcript, or conversation metadata fails explicitly; it never falls back
  to a fresh conversation. Other saved sessions remain untouched.
* Available worktree: run `dev new` with that absolute checkout path, then
  connect normally. This does not create a Git worktree or move a branch.

Scope changes only read inventory and reload private snapshots; they do not
create/restore sessions or change records. OPEN retains its initial live-session
snapshot. Esc or Ctrl-C cancels without creating/restoring sessions or changing
records. The picker has no delete actions and does not execute text from its selection.
User fzf defaults are disabled for this picker so bindings/output overrides
cannot change that contract. Use `prefix + w` to open the picker in the current
pane's directory, or run `dev switch` explicitly. `prefix + s` remains the
existing tmux session chooser.

== Persistent sessions and reboot recovery

Successful `dev new`, `dev open`, and `dev tree` calls automatically register
session intent in `${XDG_STATE_HOME:-$HOME/.local/state}/dev/sessions.json`.
There is no save command. `dev close`, `dev kill`, and merge cleanup unregister
intentional closures, including when the tmux server is already gone.
`dev merge --keep` retains the record. Exiting an agent, killing tmux outside
dev, a crash, or a reboot does not clear the registry.

When saved records exist but *no managed dev sessions are running* on the current
tmux server, ordinary `dev new`, `dev open`, and `dev tree` ask before replacing
the *entire saved workspace*. Managed sessions are those tagged with a checkout
path; unrelated tmux sessions do not suppress this prompt. This boundary applies
after any server loss, whether from a reboot, crash, or manually stopping tmux;
there is no OS reboot detection or boot-level mode.

The prompt lists every affected session name, checkout path, and branch; the
default is *No*. Noninteractive use (including `dev tree --no-attach`) fails
before creation and explains how to recover or retry interactively. Approval
replaces recovery records only, never checkouts or agent conversations, and
commits a target-only baseline only after successful creation. Failed creation
retains the previous workspace. While *any* managed dev session is running,
ordinary opens append or reuse records without prompting.

To keep the prior workspace, explicitly run `dev resume-all`, or choose one
saved entry in `dev switch`. Both preserve all saved records even if recovery
fails; selecting a saved entry restores only that exact session. If every
recovery fails and no managed sessions are running, the next ordinary open asks
again. Read-only `dev --list`, opening the picker, and OPEN/ALL toggles never
change saved intent. The version-3 registry has no boot metadata; version-1 and
version-2 files migrate on the next write, preserving all records, their data,
and insertion order regardless of obsolete boot metadata.

Run `dev resume-all` after restarting. It recreates missing sessions detached
and does not modify, select windows in, or attach to sessions already open for
a recorded path. It uses the checkout's current `devConfig.jsonc` (or the bundled
default) for standard windows, retaining the chosen agent and explicit
writing/`--nvim-command` override. It does not restore editor buffers, shell
history/processes, additional manually created windows/panes, or subagents.

Only the original configured agent pane is tracked, by its tmux pane and server
identity. The installed Pi extension records `getSessionFile()` and session ID
at `session_start`, including `/new`, `/resume`, `/fork`, and `/reload`. Claude's
metadata-only `SessionStart` hook records `session_id` and `transcript_path`,
including `/clear` and `/resume`. Neither integration reads transcript contents.
Resume uses `pi --session <exact-file>` or `claude --resume <exact-id>` with no
fallback to latest/fresh. Custom agent command flags/wrappers are not replayed
on exact resume; normal session creation still uses the configured command.
Other agent implementations are not resumable once started.

Staged agent commands remain staged after recovery. If they have never run,
the configured initial command is typed without Enter; once a conversation is
recorded, its exact resume command is staged instead. An agent window that was
intentionally empty stays empty, even if the config later adds an agent.

Missing checkouts, missing/empty/unreadable transcripts, ephemeral Pi sessions,
and missing conversation metadata fail explicitly with recovery instructions.
Records are retained, other resumable sessions are still processed, and the
command exits non-zero. Restore the exact path/file and retry; do not substitute
a different transcript. To intentionally discard a record and start over, run
`dev close` from that checkout, then `dev new`/`dev tree`.
Registry read-modify-write operations use an OS lock and atomic rename; dev's
session lifecycle operations are serialized separately so hooks can record
metadata while sessions start. A worktree startup script must not synchronously
run another dev lifecycle command: dev rejects that nested call rather than
waiting on its own lock. Run follow-up dev commands after initialization finishes.

After installing/updating, new Pi processes and Claude sessions load the
integration. A running tracked Pi can `/reload` to capture its active file;
Claude captures on the next `SessionStart`. A pre-existing tmux session opened
before tracking is registered on reuse but has no reliable agent/pane metadata:
resume fails rather than guessing its agent, overrides, or conversation. Close
and recreate that session intentionally to bootstrap tracking. Never-started
or unpersisted conversations cannot be recovered after a crash.

From the repository root:

----
./setup.sh
# Optional, only for Taylor's complete personal dotfiles:

Shared setup installs the thin command wrappers into `~/bin`, links the workflow

== tmux keybinds

Prefix is `M-Space` (Meta+Space), or `C-b` (Ctrl+B) when Meta is unavailable.
Both prefixes work with every shortcut below. Press Ctrl+B twice to send a
literal Ctrl+B to the pane (useful for nested tmux).

After either prefix:

* `n` -> local dev session (`dev new`)
* `N` -> local dev session (`dev new`)
* `t` -> new worktree session (`dev tree`)
* `W` -> new worktree session (`dev tree`)
* `M` -> run `dev merge` in-pane (interactive target prompt)
* `c` -> create a shell window in the current directory; its tab is named for that directory
* `&` -> hide the current window without stopping its pane processes
* `w` -> searchable dev session/worktree picker (`dev switch`); replaces tmux's default window chooser
* `s` -> open the native tmux session chooser; it labels sessions as `attached` or `detached`
* `?` -> show tab/control keyboard help in the tmux message area

== Clickable tmux tabs

The status bar has a clickable `×` on every window tab, followed by `+` and
`◌` controls. Clicking a tab selects it; clicking its `×` *hides* it rather
than killing it. Hidden windows are linked into the private
`__tmux_hidden_windows__` session, so their shells, editors, and other pane
processes remain alive. Use `◌`, click the session name in the status bar, or
press `prefix + s` to open tmux's interactive session chooser and switch to
that session when you want to reconnect. The chooser displays `attached` for
sessions with a connected client and `detached` otherwise.

`+` (or `prefix + c`) opens a new idle shell window rooted at the current
pane's directory and names its tab after that directory.

Terminal mouse protocols do not provide a portable hover event, so tmux cannot
show conventional hover tooltips. The visible tab number is its keyboard
shortcut (`prefix + 1` through `prefix + 9`), and `prefix + ?` displays the
complete keyboard equivalents for tabs and controls.

== Recommended repo layout

[source,text]
----
/path/to/project-name             # main checkout
/path/to/project-name-worktrees   # worktrees
----

`dev tree` creates worktrees under `<repo-name>-worktrees/<branch>`. If the
requested branch is currently checked out in the primary checkout, `dev tree` warns
and offers to move it into that directory. Confirming requires a clean primary
checkout; `dev tree` checks out the repository's `origin/HEAD` (or `main`/
`master`) there before creating the worktree. The optional base argument keeps
its usual meaning: the base for a newly created branch.

When creating a new branch, `dev tree` bases it on your current branch by default.
If your current HEAD is detached, it falls back to `main`. If no matching local
branch exists and the repository has an `origin` remote, `dev tree` asks before
fetching `origin`. When `origin/<branch>` exists after that fetch, it creates a
local branch that tracks it; otherwise it creates the new branch from the base.
`dev tree` now reuses tmux sessions by matching the resolved worktree path, so `dev tree B`
from worktree `A` reconnects only to the session already bound to the same worktree path.
If a session named for branch `B` already exists but points at some other checkout,
`dev tree` creates a new suffixed session instead of attaching you to the wrong worktree.

`dev new` follows the same rule for non-worktree sessions: it reuses the session for the
resolved project path, and if the preferred `<repo>-dev` name is already attached to
some other checkout, it creates a suffixed session instead of reusing the wrong one.

== Killing a worktree

Use `dev kill` from inside a worktree session when you want to discard that worktree
without merging it anywhere.

* `dev kill` -> close the current branch's worktree, kill its tmux session, and delete the local branch
* `dev kill my-branch` -> close a specific branch worktree
* `dev kill <path>` -> close the worktree containing a path, including a detached one
* `dev kill --force` -> allow closing a dirty worktree and force-delete the local branch
* `dev kill --yes` -> skip the confirmation prompt, while keeping the dirty and unmerged checks

When `git branch -d` refuses an unmerged branch, `dev kill` has already removed
the worktree; it still closes the session, keeps the branch, and exits non-zero.

`dev kill` refuses to remove the main checkout, and it protects `main`, `master`,
`develop`, and `staging` unless you pass `--force`.

== Closing a session only

Use `dev close` when you want to shut down the tmux session but keep the repo or
worktree exactly as-is.

* `dev close` -> close the current repo/worktree dev session
* `dev close my-branch` -> close the tmux session for a specific worktree branch

`dev close` uses the same session-resolution rules as `dev new` and `dev tree`, so it closes
the session attached to the resolved path even when a suffixed fallback session name
was used.

When you run `dev close` or `wclose` from inside the current tmux dev session, tmux switches
you to the most recently used remaining managed dev/writing session before closing the
current one.

== Worktree startup

Before opening a newly created worktree session, `dev tree` runs one startup script. Run
`dev tree init [branch]` to rerun that script later without creating a session; it defaults
to the current branch's linked worktree and rejects the primary checkout.
It uses the first non-empty project-specific script it finds in the main checkout:

* `.worktree-init.sh`
* `scripts/worktree-init.sh`

Otherwise, it runs the bundled example script,
`bin/lib/worktree-init-example.sh`. The example:

* symlinks `.env` from the main checkout when it exists
* runs `npm ci` when `package-lock.json` exists
* symlinks Terraform state files (`terraform/**.tfstate` and `terraform/**.tfstate.*`) and
  variable files (`terraform/**.tfvars`) from the main checkout when they exist

Copy that example into one of the project-specific locations and adapt it for
project setup. The script runs with its working directory set to the new
worktree and receives `REPO_ROOT` (the main checkout) and `WORKTREE_PATH` (the
new worktree) as environment variables.

== Non-interactive worktrees

`dev tree --no-attach <branch>` is for scripts. It creates or reuses the
worktree and its tmux session exactly as `dev tree` does, runs the startup script
for a new worktree, and records the session, but never attaches and never
prompts. All progress, including git and startup-script output, goes to
stderr; stdout carries only the worktree path. The startup script gets no
stdin and not the caller's stdout, so a process it leaves running in the
background cannot keep the caller waiting. Where `dev tree` would ask, it
takes the safe path or fails with a message on stderr:

* it never fetches `origin`; a new branch starts from the base;
* it fails when `origin/<branch>` is already known locally, rather than
  silently creating an unrelated branch of the same name;
* it fails when the branch is checked out in the primary checkout, from any
  worktree, rather than switching that checkout or printing its path;
* it fails when the default path exists but is not that branch's worktree.

`home/.claude/settings.json` (added to `~/.claude/settings.json` by
`./setup.sh`, or linked whole by `./setup-personal.sh`) registers two hooks from `home/.claude/hooks/`, so Claude Code's
worktrees follow dev's layout instead of `<repo>/.claude/worktrees/`:

* `WorktreeCreate` -> `worktree-create.sh` runs
  `dev tree --no-attach --agent claude --stage-agent -- <name>` in the session's
  directory. The worktree lands at `<repo-parent>/<repo>-worktrees/<name>` on
  branch `<name>`, based on that directory's current branch, the startup script
  runs, and a detached dev session is created. Its agent window has
  `claude --continue || claude` typed but not run: the Claude session that asked
  for the worktree is already running, and starting the TUI then would begin a
  second, separate conversation. A project whose `devConfig.jsonc` has no agent
  window or no `claude` agent still gets the worktree, with a warning and no
  agent typed. A name that already has a worktree reuses it.
* `WorktreeRemove` -> `worktree-remove.sh` runs `dev kill --yes` on the path,
  which also closes the session and deletes the branch. It never forces: a
  dirty worktree is refused and stays on disk (the hook fails), and an unmerged
  branch is kept: the worktree is still removed, so the hook succeeds and
  reports the kept branch on stderr.

Both hooks add Homebrew's `bin` directories (`$HOMEBREW_PREFIX/bin`,
`/opt/homebrew/bin`, `/usr/local/bin`) that exist and are missing from `PATH`
to its front, because the desktop app runs hooks with the GUI's `PATH`, which
usually lacks them, and `dev` needs tmux.

The hooks fire for `claude --worktree`, for subagents with
`isolation: worktree`, and for background sessions, and they replace Claude's
git logic entirely. Some consequences of that:

* `.worktreeinclude` is not processed; use the startup script (`.env` linking
  is already in the bundled example).
* `worktree.baseRef` is ignored; the base is the current branch, as for `dev tree`.
* Every subagent worktree also gets a dev tmux session, and Claude's periodic
  sweep never removes hook-created worktrees, so leftover subagent worktrees
  stay until you `dev kill` them.
* Claude never deletes a hook worktree's branch itself; `dev kill` does.

To move a session from the app to the TUI, stop using it in the app, attach
with `dev tree <name>`, and press Enter in the agent window; `claude --continue`
resumes the conversation. This works for desktop-app sessions because the app
runs the session with the hook's worktree as its directory and records the
transcript there. A terminal
`claude --worktree` session keeps its transcript under the directory it was
launched from, so `--continue` in the worktree starts a new conversation
instead. Use one client at a time: running the same conversation in the app and
the TUI at once is untested.

=== Claude desktop app

The desktop app runs the same `WorktreeCreate` hook when you start a new local
session with the worktree option in a folder whose settings configure one
(verified with app-created session names such as `first-message-test-ad03fe`).
It then uses the printed path, with the worktree name as the branch (no branch
prefix), and runs `WorktreeRemove` when you delete the session and it cleans the
worktree up. The app refuses repositories under a Claude session's scratch
space (`/private/tmp/claude-*`), so test it with a repository elsewhere. The desktop
app runs the hook only for a session a person starts in that folder; it refuses
to create a worktree for a repository with a hook when nobody opened that
folder.

Without the hook, the fallback is the desktop's *Worktree location* setting
(Settings -> Claude Code). It can move worktrees out of the project to one folder
you choose, with a subfolder per repository. It cannot express dev's layout: no
per-repository `<repo>-worktrees` sibling folder, branches still get the desktop
branch prefix (`claude/<name>` by default), and it runs no startup script and
creates no tmux session. `dev close`, `dev kill`, and `dev merge` still work on
those worktrees by branch or path.

The dev tests use isolated HOME/XDG state and fake tmux. The picker suite also
uses fake fzf and real throwaway Git worktrees, times each test, and bounds each
command to eight seconds (90 seconds for the suite). It verifies saved opening
order across reuse, close/reopen, recovery, and pretracking sessions, selected-only
recovery, and that attachment occurs after lifecycle lock release, without a
live tmux server or user registry/transcripts. The real-fzf smoke uses a
controlling pseudo-terminal with isolated HOME/XDG and fake tmux, tests OPEN/ALL
reloads in both directions (including an empty OPEN scope), unchanged state
while toggling, retained queries, selection after reload, opening-order default
selection, and standard nonempty-query match ranking. It requires fzf
and is bounded to ten seconds per picker / thirty seconds for the suite.
`python3 tests/dev-picker-loading.fzf.test.py` adds real-fzf PTY flows with
blocked fake discovery: zero initial Git probes and one registry ordering read,
Loading and native spinner visible before release, fresh ALL data with retained queries, actionable
failure, and rapid toggle/cancel without leaked discovery processes. It uses
isolated HOME/XDG and bounded process groups (50-second suite limit).
The binding smoke test uses an
isolated tmux server and attached pseudo-terminal to exercise both prefixes
through `dev switch`, with a cancelling fake fzf. The real-tmux recovery smoke
test uses a private server/socket and synthetic agent processes through the
actual lifecycle adapters; it does not call an LLM or access user transcripts.
